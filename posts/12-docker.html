第 4 週：Docker、compose 與 CI，一行指令跑起整個系統

約 10 分鐘Dockerdocker composeCI

第 4 週的目標很單純：讓任何人在乾淨的電腦上，用一行指令就能把整個系統跑起來。前三週我都是在 IDE 裡一個一個服務啟動，這週把它們全部放進容器。這篇記錄 Dockerfile 的寫法、docker compose 怎麼安排啟動順序與對外的門，以及一個看起來像錯誤、其實是我自己設定問題的 log。

一行指令

docker compose up --build

第一次要下載依賴，需要幾分鐘；之後有快取，很快。啟動後開 http://localhost:8088 就是操作台。所有模擬資料都是虛構的，資料庫與訊息佇列的密碼也只是開發用的假值，檔案開頭有註明不要拿去別處用。

Dockerfile：分成兩階段

每個 Java 服務的 Dockerfile 都是同一個形狀：

# 階段一:用 JDK 編譯(含 Maven 快取)
FROM eclipse-temurin:21-jdk AS build
RUN --mount=type=cache,target=/root/.m2 ./mvnw -q package -DskipTests

# 階段二:只留執行需要的 JRE 與 jar
FROM eclipse-temurin:21-jre
RUN useradd --system app
USER app
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=75", "-jar", "app.jar"]
  • 兩階段：編譯需要 JDK 與一堆原始碼，執行只需要 JRE 與一個 jar。最後的映像檔只含後者，更小、攻擊面也更小。
  • 快取掛載：Maven 下載過的依賴放在建置快取裡，改一行程式不用重新下載全部。
  • 非 root 使用者：容器裡的程式不需要管理員權限，萬一被入侵，能做的事也少一些。
  • MaxRAMPercentage=75：告訴 JVM 用容器記憶體上限的 75% 當堆積上限。不設的話，舊版 JVM 會以為整台機器的記憶體都能用，容易在容器裡被系統殺掉。
給 .NET 開發者的對照

兩階段建置就像 .NET 的 mcr.microsoft.com/dotnet/sdk 編譯、再複製到 aspnet 執行映像檔。概念完全一樣，只是名字不同。

前端操作台則是先用 Node 建置出靜態檔，再放進 nginx 提供。API 的網址是在建置時用參數 VITE_API_BASE 寫進去的，因為靜態檔跑在瀏覽器，沒有環境變數可以讀。

docker compose：誰能被看見，誰要先起來

只開三個門

整套系統在 compose 的內部網路裡，服務之間用名稱互相呼叫（例如 http://equipment-service:8082）。對外只開三個埠：閘道 8080、操作台 8088、RabbitMQ 管理頁 15672。資料庫與各服務都不對外，想用 API 一律走閘道，所以角色規則（第 9 篇）不會被繞過。

啟動順序：用健康檢查，不要用「先後順序」

第 3 篇提過 queue 由消費者宣告，消費者還沒啟動就送出的事件會消失。在 compose 裡的解法是 depends_on 加上健康檢查（healthcheck）：

equipment-service:
  depends_on:
    alarm-service: { condition: service_healthy }
    postgres:      { condition: service_healthy }

「容器已啟動」不等於「服務準備好了」。condition: service_healthy 會等到健康檢查通過才啟動下一個，所以 alarm-service 先宣告好它的 queue，事件才不會掉。

種子工作與選用的模擬器

一個一次性的 seed 容器會透過閘道註冊三台機台，做完就結束；模擬器放在 simulator 這個 profile 裡，要加 --profile simulator 才會啟動。這樣預設是一個安靜、可以手動操作的系統，需要熱鬧時再開模擬器。另外還保留 deploy/docker-compose.yml，只含基礎設施（資料庫與 RabbitMQ），給在 IDE 裡開發的人用。兩份 compose 用同樣的埠，不要同時跑。

一個看起來像錯誤的 log

系統跑起來後，資料庫容器的 log 每隔幾秒就出現一行：

FATAL:  database "fab" does not exist

看起來很嚴重，但服務一切正常。原因是我的健康檢查寫成 pg_isready -U fab。沒指定資料庫時，它預設會連到和使用者同名的資料庫 fab，而這個資料庫根本不存在（每個服務各有自己的資料庫名稱）。連線被拒，於是在 log 裡留下 FATAL，但 pg_isready 本身仍然回報「資料庫可連線」，所以才不會影響健康判斷。

修法是把資料庫名稱也寫進去：pg_isready -U fab -d $${POSTGRES_DB}（雙錢字號是讓 compose 不要自己展開，而是交給容器裡的 shell）。

這次學到的

看到 FATAL 先不要慌，也不要直接忽略。先確認服務有沒有真的受影響，再去找是誰在製造這行 log。很多時候是自己的監控工具造成的雜訊，但雜訊多了，真正的錯誤就容易被蓋住。

CI：把映像檔推到 GHCR

新增的 GitHub Actions 工作流程會在每次變更時為七個元件（六個服務加操作台）建置映像檔；只有推到 main 時才會推到 GitHub 的容器登錄服務 ghcr.io，PR 只建置、不推送。這也是第 5 週用 Kubernetes 和第 6 週做部署驗證的前提：部署的來源是已經建好、有版本標記的映像檔，而不是原始碼。

如何驗證

  1. docker compose up --build，等到看見 Seed done.。
  2. 開 http://localhost:8088，用 admin 登入，能看到三台機台。
  3. 執行 scripts/demo.ps1，它會依序走過登入、查詢、改狀態、告警確認，全部 ok 即通過。
  4. docker compose --profile simulator up -d 加入模擬器，觀察機台自己跑起來。
  5. 停止：docker compose --profile simulator down（資料保留；加 -v 連資料一起刪除）。
