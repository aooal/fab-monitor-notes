第 6 週（一）：CI 部署冒煙測試，每次都在新叢集上把系統裝起來

約 9 分鐘GitHub ActionskindHelmCI

第 5 週結束時，系統已經能用 Helm 裝進 Kubernetes，但有一個洞：這些東西全靠我在自己電腦上手動驗證。改了 deploy/helm/** 沒有任何自動檢查，helm install 會不會壞，要等下次手動跑才知道。第 6 週的第一件事，就是讓 GitHub Actions 每次都在一個全新的 Kubernetes 叢集上把整個系統裝起來、用一遍。這篇記錄它的原理、每一步的用意，以及它能抓到與抓不到的東西。

為什麼單元測試不夠

前幾週的 234 個測試測的是程式邏輯：狀態機、規則、API。但第 5 週我踩到的坑，幾乎沒有一個是這些測試能抓到的：lot-service 在叢集裡因為多出來的 RABBITMQ_PORT=tcp://… 環境變數而當掉；種子 Job 太早呼叫閘道拿到 500；auth-service 的金鑰各 pod 不一致。這些問題都出在「程式和環境接起來的地方」，而不是程式本身。所以需要一種測試，是把整個系統真的裝起來再檢查。

給 .NET 開發者的對照

單元測試像測單一個類別；WebApplicationFactory 的整合測試是把一個服務整個啟動後打 HTTP。冒煙測試再往外一層：把整套系統加上部署設定一起啟動，再從外面打進去。GitHub Actions 的角色像 Azure Pipelines。

什麼是冒煙測試

名字來自電子硬體：新電路板接上電，先看會不會冒煙，不冒煙才值得往下測。軟體上一樣：不測細節，只確認「系統站得起來、主要流程通」。我的冒煙測試問的是：chart 裝得起來嗎？登入得了嗎？種子資料有進去嗎？換掉 auth-service 之後 token 還有效嗎？升級與回滾做得到嗎？

運作原理

GitHub Actions 每次執行會給你一台臨時的 Linux 虛擬機（runner），上面有 Docker，跑完就銷毀。所以流程和我在本機做的一模一樣，只是由機器代勞，而且每次都從零開始：

  1. 觸發：改了 deploy/helm/**、deploy/kind-cluster.yaml、services/**、frontend/** 或這個 workflow 本身就執行，也可以在網頁上手動執行。
  2. 建映像檔：六個映像檔用標籤 :ci 在 runner 上建好，不推到任何地方（權限只有 contents: read，不需要也不能推）。建置的快取與「Docker images」那條 workflow 共用，同一份程式碼不會建兩次。
  3. 建拋棄式叢集：用 helm/kind-action 搭配和本機同一份 kind-cluster.yaml 建 kind 叢集，再用 kind load 把映像檔塞進去。
  4. 建 JWT 金鑰 Secret：用 openssl 當場產生一把只屬於這次執行的金鑰。私鑰仍然不在 Git 裡，用完連 runner 一起消失。
  5. 安裝：先 helm lint，再 helm install --wait。--wait 會等所有 Deployment 與 StatefulSet 就緒，並等種子 Job（Helm hook）跑完才回傳。
  6. 冒煙測試：用 curl 像使用者一樣打：操作台首頁有回應；沒帶 token 打 /api/alarms 要得到 401；用 admin 登入拿 token；機台清單至少 3 台（證明種子 Job 有跑）；接著 kubectl rollout restart 把所有 auth-service pod 換掉，同一個 token 再打一次要得到 200。
  7. 升級與回滾：helm upgrade --set gateway.replicas=2 後檢查份數是 2，helm rollback fab 1 之後檢查變回 1。
  8. 失敗時：自動印出 pod 狀態、describe、各服務 log 與叢集事件。看 log 的人不用再另外重現。

幾個設計決定

用 values-ci.yaml 處理 runner 的限制

同一個 chart，CI 用另一份 values 檔，這正是 Helm 的用處。和本機相比只有三種差異：

  • 映像檔：前綴改成 fab-monitor-、標籤 ci、pullPolicy: Never。只用塞進叢集的那一份，絕不去網路下載。
  • 資源要求調小：runner 的 CPU 比較少，要求太多 pod 會排不進去。記憶體上限不變，避免掩蓋真的會 OOM 的問題。
  • 關掉 HPA：測試叢集沒有 metrics-server，HPA 會一直等不到數據。

auth-service 則故意保留 2 份，因為這個測試的重點之一，就是證明兩個 pod 共用同一把金鑰。

測的是行為，不是「有沒有 Running」

pod 顯示 Running 不代表系統能用。所以測試是從閘道打進去，走完登入、查詢、換 pod 後再查。尤其「換掉 auth-service 後 token 仍有效」這一步，把第 5 週手動做的那個實驗變成每次都會自動重跑的檢查。如果有人日後不小心把金鑰又改回「每個 pod 自己產生」，這一步會直接變紅燈。

失敗時要有證據

CI 失敗時 runner 就要銷毀了，你沒辦法事後上去看。所以最後一步 if: failure() 會在失敗時把叢集狀態印進 log。這個習慣和第 6 篇的「把兩大段 stack trace 縮成一行」是同一個道理：出事時最需要的是有證據可看。

它能抓到、抓不到什麼

抓得到：樣板語法錯誤、values 組合錯誤、映像檔啟動失敗、探針設錯、init container 卡住、Secret 少了、服務之間連不上、金鑰不一致、升級或回滾壞掉。

抓不到：效能與負載（HPA 在這裡是關的）、資料持久性（叢集每次都是新的）、真實的雲端行為（AKS 的儲存、Ingress、Key Vault）、以及單元測試才測得到的細節邏輯。這些要靠其他測試，或日後在真的叢集上驗證。它是第一道防線，不是全部。

為什麼我沒有做「自動上線」

一般的流程會在測試通過後，把新版本自動部署到正式環境（CD）。這個專案我刻意不做，理由有三個。第一，它沒有正式環境，也沒有真正的使用者；第二，租一個雲端叢集要花錢，忘了關還會持續計費；第三，上線前最容易出錯的環節（chart 能不能安裝、升級、回滾，服務之間連不連得上），已經由這個冒煙測試在全新叢集上驗證過了。真要上線，只需要多一個 values 檔和一個部署步驟，不需要重做設計。我把這個取捨寫進了 ADR 0006。

如何驗證

  1. 推送後到 GitHub 倉庫的 Actions 頁籤，找到「Kubernetes smoke test」，看每個步驟的狀態。
  2. 也可以在該頁面按「Run workflow」手動觸發，不用改任何檔案。
  3. 想看它真的會抓到問題：在新的分支故意把 deploy/helm/fab-monitor/templates/auth-service.yaml 裡的金鑰掛載拿掉，推上去，「換掉 auth-service 後 token 仍有效」那一步應該會變紅；再還原。
