訊息會重複送達：冪等消費與交易

約 9 分鐘冪等交易PostgreSQL

RabbitMQ 保證的是 at-least-once（至少送達一次），不是 exactly-once。換句話說：同一則訊息，可能來兩次。例如消費者處理完、還沒回報「收到」就當機，RabbitMQ 會把訊息再送一次。

如果處理的是「機台 EQP-01 進站 LOT-1」，做兩次可能第二次就失敗，或更糟：悄悄把資料弄錯。解法是讓消費者變成冪等（idempotent）：同一則訊息處理一次或十次，結果都一樣。

做法：記下「我處理過這個 eventId」

每個服務有一張 processed_event 表，只存已處理過的 eventId。處理訊息前先嘗試寫入（以下為簡化示意）：

INSERT INTO processed_event (event_id, processed_at)
VALUES (?, now())
ON CONFLICT (event_id) DO NOTHING

這句 SQL 會回傳影響的列數。1 代表第一次看到，可以處理；0 代表重複，直接略過。因為判斷與寫入是同一個原子操作，兩個消費者同時搶也不會都通過。

關鍵：標記與業務變更在「同一個交易」

順序很重要。比較三種寫法：

寫法中途當機的後果
先標記「已處理」，再改業務資料（不同交易）標記成功、業務沒改 → 重送時被當成重複略過，資料永遠漏掉
先改業務資料，再標記（不同交易）業務改了、標記沒寫 → 重送時再做一次，重複套用
同一個交易（本專案採用）要嘛都成功、要嘛都回滾 → 重送時乾淨地重來
@Transactional
public void machineTrackIn(UUID eventId, String lotNo, String step) {
    if (!processedEvents.markProcessed(eventId)) return;  // 重複 → 略過
    // 找 lot、套用變更;任何地方丟例外,上面的標記一起回滾
    ...
}
給 .NET 開發者的對照

@Transactional 就是把整個方法包進 TransactionScope（或 EF Core 的 SaveChanges 單一交易），例外一丟就回滾。「Inbox pattern」是這種做法在 .NET 圈的常見名稱。

如何確認它有效？

寫了三個 Testcontainers 整合測試，其中最重要的一個叫「回滾後可以再成功」：

  1. 送一則會失敗的事件（例如 lot 不存在）→ 例外 → 交易回滾。
  2. 確認 processed_event 裡沒有這個 eventId。
  3. 先把 lot 補進去，再送同一則 eventId → 這次成功。

這證明「失敗不會留下假的已處理紀錄」。如果標記是獨立交易，這個測試會失敗。

實測也看得到這個行為

在 RabbitMQ 管理介面手動補發訊息時，如果重複使用舊的 eventId，系統會當成重複而略過；換新的 UUID 才會真的處理。這正是冪等的預期行為。

已知限制：發布端也可能遺失事件

消費端做好了，發布端還有一個洞。equipment-service 目前是「資料庫交易提交之後」才發布事件（publish-after-commit）。如果提交成功、但發布前當機，資料變了而事件沒發出去。

標準解法是 Outbox pattern：把「要發布的事件」跟業務資料寫進同一個交易，再由另一個程序把它送出去。目前列為後續改善項目，並在 README 中標明這個限制。

另一個設計取捨

equipment-service 與 lot-service 各自獨立消費同一則機台事件。如果其中一個拒收而另一個成功處理，兩邊會暫時不一致。目前接受這個取捨，日後可以加入「對帳」機制來偵測差異。
