機台模擬器：沒有真機台，就自己造事件

約 10 分鐘模擬器設計取捨

為了讓整條事件流能在本機完整跑起來，我做了 equipment-simulator：它扮演三台機台（EQP-ETCH-01、EQP-ETCH-02、EQP-LITHO-01），定時把事件丟進 RabbitMQ。

模擬的是什麼

  • 每批 Lot 25 片晶圓，依序經過五個站點：LITHO → ETCH → CVD → CMP → IMPLANT。
  • 機台進站、出站，偶爾故障（DOWN 機率 5%），之後再恢復。
  • 每次啟動產生一組新的批號前綴，例如 LOT-10081531-，避免和上次跑的撞號。

設計一：核心邏輯是純 Java

「這一個 tick 該發什麼事件」的邏輯放在 FabSimulation，不依賴 Spring、不依賴 RabbitMQ，只透過一個介面把事件交出去。好處是可以用單元測試驗證，而不用真的開 RabbitMQ。

它還接受一個隨機種子：同樣的種子跑出同樣的事件序列。這讓測試可以重現：「種子 42 時第 7 個 tick 應該機台故障」是個確定的斷言，不會有時過、有時不過。

給 .NET 開發者的對照

就像把 new Random(seed) 傳進去而不是在裡面 new Random()；把時間也當參數傳（Clock），測試才不會被「現在幾點」影響。

設計二：故意送壞訊息

真實世界一定會有壞資料。模擬器有 2% 的機率對 machine.track-in 送一則格式錯誤的訊息（例如 eventId 不是 UUID）。目的是讓死信佇列有東西可看，也驗證消費者面對壞資料時不會卡死。

設計取捨：找不到 lot 要不要自動建立？

lot-service 訂閱 track-in 事件時，如果事件裡的 lot 不存在，直覺的做法是「自動建一筆」，但這行不通：

做法問題
找不到就自動建立建立一批 Lot 需要產品代號與數量，而 track-in 事件根本沒有這些資料。要不就填假值（資料變髒），要不就改事件塞進不屬於它的欄位。
找不到就丟死信佇列資料完整性有保障，但需要有人負責「先建立 Lot」。
新增 lot.created 事件（採用）建立批次是一個獨立的事實，由來源明確宣告；之後的事件找不到 lot 才是真正的異常。

所以模擬器在第一次提到某批 Lot 之前，會先發一則 lot.created。lot-service 收到就建立批次（已存在則忽略，冪等）。而「消費者絕不憑空捏造資料」成了契約裡的原則。

這也是業界常見的想法：資料的擁有者負責宣告它的誕生，下游不要猜。

改善：啟動時對齊機台狀態

實測時發現：每次停掉模擬器再啟動，機台的真實狀態還留在 equipment-service（例如某台仍握著一批 Lot，或是 DOWN），模擬器卻以為全部閒置，於是新的事件與現況對不上而被拒收，必須手動到 RabbitMQ 修復。

原因很單純：模擬器有自己的記憶，真實狀態在另一個服務裡。兩邊的記憶不一致。

解法是「啟動時對齊」：模擬器啟動時先呼叫 equipment-service 的 REST API 讀取三台機台的真實狀態，再從那個狀態接著模擬。若 equipment-service 還沒開，模擬器不會亂猜，而是記一行警告，每個 tick 重試，直到三台機台都問到為止才開始發事件。對齊的開關（simulator.align-on-start）可以關掉。

業界也這樣做嗎？

思路相同：任何「帶有本地狀態的元件」重啟時，都應該先與真實來源（source of truth）同步，而不是假設從零開始。這跟服務啟動時重建快取、消費者從上次 offset 繼續是同一個概念。

啟動順序提醒

RabbitMQ → lot-service、equipment-service → 註冊機台 → 模擬器。原因見前一篇：queue 是消費者宣告的，模擬器太早發訊息會沒有人接。
