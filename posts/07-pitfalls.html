踩坑紀錄:每個坑怎麼發現、怎麼修

約 7 分鐘除錯經驗

做專案最有價值的常常不是順利的部分。這篇把實際遇到的問題整理成表,每一個都寫「症狀 → 原因 → 修法 → 學到什麼」,方便日後遇到類似狀況時回頭查。

一覽表

#症狀真正的原因修法
1機台卡在 DOWN,手上還握著一批 Lot,無法設回 IDLE(回 409)同時開了兩個模擬器(舊版用不同的批號),互相干擾全部停掉 → 手動出站 → 設 IDLE → 清空死信佇列 → 只開一個
2手動補發的出站訊息沒有效果重複使用舊的 eventId,被冪等機制當成重複略過每次手動送訊息都換新的 UUID
3lot-service 的死信佇列根本不存在lot-service 沒用新版本重啟,queue 從未被宣告重啟服務;並記下啟動順序
4lot.created 發了但批次沒建立當時沒有任何 queue 綁定該 routing key,訊息被丟棄且不報錯固定啟動順序:RabbitMQ → 服務 → 模擬器
5我一度建議「找不到 lot 就自動建立」建立 Lot 需要產品代號與數量,track-in 事件沒有撤回建議,改設計 lot.created 事件
6呼叫 GET /api/lots 找不到那個端點當時還沒寫(我太早叫自己測)先用 by-lot-no 查,隨後補上列表 API
7模擬器每次重啟都要手動重設機台模擬器的記憶和 equipment-service 的真實狀態不一致加上「啟動時對齊」
8測試編譯錯誤:重複的 import用 sed 批次修改時多加了一次 import java.util.HashMap手動移除;批次修改後務必檢查結果
9啟動報錯:Spring 不知道該用哪個建構子類別有多個建構子,Spring 無法選擇只保留一個建構子
10CI 設定了 PostgreSQL 服務卻不需要整合測試已改用 Testcontainers,自己起容器移除 workflow 裡的資料庫服務並加註解
11推上 GitHub 被拒:需要 workflow 權限推送的 commit 含有 .github/workflows,Token 缺少對應範圍補上 workflow scope(或改用登入授權)
12每個失敗訊息印出兩大段 stack trace、白等 3 秒所有例外一律重試,且兩個框架元件各印一次見前一篇:區分業務/技術錯誤、單行 log

三個我最想記住的

1. 「狀態有兩份」就會出問題(#1、#7)

模擬器存一份機台狀態,equipment-service 也存一份。它們一不同步,系統就進入怪狀態,還得手動修。教訓是:要嘛只有一份真相,要嘛有明確的同步方式。這個坑後來變成「啟動時對齊」的功能。

2. 靜默失敗最難查(#4)

訊息因為沒有 queue 綁定而消失,系統完全不報錯。RabbitMQ 有「mandatory」旗標與 publisher return 機制可以偵測這種情況,但我目前接受這個限制並寫在文件裡。之後若要補強,可以讓發布端在無路由時記錄警告。

3. 錯誤要能被重現、被看見(#12)

模擬器的故意壞訊息,讓我有穩定的素材去觀察失敗路徑。而 log 一旦太長,等於沒有 log。能被快速讀懂,才算可觀測。

給未來的自己

遇到「系統狀態怪怪的」,先確認有沒有多個副本同時在跑(#1)、服務是不是用新版本重啟了(#3),再往深處查。九成的問題在這兩步就解決了。
