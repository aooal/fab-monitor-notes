為什麼做 Fab Monitor?整體架構一次看懂

約 8 分鐘架構微服務

半導體製造是我很有興趣、但完全沒有實務經驗的領域。所以我決定用「模擬」的方式,自己做一個小型的批次與設備監控平台,把微服務、訊息佇列、容器化與 CI/CD 一次練完整。

先說清楚

這是模擬專案。所有批次、機台與事件都由程式產生,流程是我依公開概念簡化出來的,不代表任何真實工廠或其內部系統的做法。

要解決的情境

晶圓在工廠裡是一批一批(Lot)流動的。每一批要經過許多站點(Step),每一站由一台機台(Equipment)處理:機台「進站」(track-in)開始加工,「出站」(track-out)送往下一站。機台也可能閒置、運轉,或故障(DOWN)。

如果要做一個監控平台,就會需要回答這幾件事:

  • 這批 Lot 現在在哪一站?是在加工中、被擋住(ON_HOLD)還是已完成?
  • 這台機台現在是閒置、運轉還是故障?手上是哪一批?
  • 機台故障了,誰來通知?

架構:四個服務,一條事件匯流排

為什麼要拆成多個服務?

老實說,這個規模用一個應用程式就能做完。拆開是為了練習那些「拆開之後才會遇到」的問題:服務之間怎麼溝通、訊息重複怎麼辦、其中一個服務壞了會怎樣、怎麼各自部署與擴縮。這些是實務上真正花時間的地方。

給 .NET 開發者的對照

每個服務就像一個獨立的 ASP.NET Core 專案,各有自己的資料庫。服務之間不共用資料表,只透過 REST 或訊息溝通。這跟你把一個大 solution 拆成多個可獨立部署的 Web API 是同一件事。

幾個一開始就定下來的原則

  • 每個服務自己的資料庫。lot-service 用 5432,equipment-service 用 5433。
  • 服務之間用事件溝通。事件的格式寫成文件(事件契約),不是口頭約定。
  • 分層要守規則。領域層不能認識框架,應用層不能認識 Web;而且用測試擋住,不靠自律。
  • 先做小、每週交付。每週都有一個可以啟動、可以測試、可以展示的成果。
  • 重要決策寫成 ADR。例如「為什麼用 RabbitMQ」,日後才知道當時怎麼想。
