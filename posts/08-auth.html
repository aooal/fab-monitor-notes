第 3 週（二）：auth-service，RS256 JWT 與會輪替的 refresh token

約 11 分鐘JWT安全Spring Security

系統需要登入，但我不想只做一個「帳號密碼對就放行」的玩具。這篇記錄 auth-service 的設計：為什麼用 RS256 簽章的 JWT，為什麼 access token 只有 15 分鐘，以及會自動換新、而且能偵測被偷走的 refresh token。

先講結論：兩種 token

Access tokenRefresh token
長相JWT（RS256 簽章）隨機字串，不是 JWT
有效時間15 分鐘7 天
用途每個 API 請求都帶，閘道驗證只拿來換新的 token，只給 auth-service
伺服器存什麼什麼都不存（自帶簽章）只存 SHA-256 雜湊
可以撤銷嗎不行，只能等過期可以

為什麼是 RS256，不是 HS256？

HS256 用同一把祕密金鑰簽章與驗證，每個要驗證 token 的服務都要拿到這把金鑰，而有金鑰就能自己「偽造」token。RS256 是非對稱的：私鑰只在 auth-service，負責簽發；公鑰公開在 /.well-known/jwks.json，任何人（包含閘道）都能驗證，但沒有人能用公鑰簽出新的 token。閘道被攻破，也拿不到能簽 token 的東西。

token 的標頭有 kid（公鑰的指紋），閘道靠它在 JWKS 裡找到對的那一把，將來換金鑰時新舊並存也不會亂。

為什麼 access token 只有 15 分鐘？

JWT 有一個性質：簽出去就收不回來，伺服器沒有「登出這個 token」的辦法，只能等它過期。如果有效期是 8 小時，token 被偷的人就有 8 小時可以用。我一開始曾考慮設 8 小時，因為使用者不用常常重新登入；後來改回業界常見的 15 分鐘，把「不用重新登入」的體驗交給 refresh token 處理。

操作台在 token 失效（回 401）時，會自動拿 refresh token 換一組新的，再重試剛才失敗的請求，使用者完全沒感覺。

Refresh token：每用一次就換新

refresh token 是 256 位元的隨機字串。資料庫只存它的 SHA-256 雜湊，所以資料庫外洩也拿不到可用的 token（跟密碼不存明文是同一個道理；因為它本身是高熵隨機值，雜湊用 SHA-256 就夠，不需要像密碼那樣用 BCrypt）。

每次拿它換新 token，舊的就作廢，同時發一個新的，這叫輪替（rotation）。重點在下面這段：

if (token.isRevoked()) {
    // 已經用掉的 token 又出現了:可能是程式錯誤,也可能是被偷走。
    int revoked = refreshTokens.revokeAllActive(token.getUserId(), now);
    log.warn("Refresh token reuse detected ...");
    throw new InvalidRefreshTokenException();
}

如果一個「已經用過」的 refresh token 又被拿來用，代表同一份 token 在兩個地方出現了：正常使用者和偷走它的人，其中一方會先用、另一方後用。系統無法判斷誰是誰，所以直接撤銷這個使用者所有進行中的 refresh token，兩邊都得重新登入。被偷走的 token 因此最多只能撐到下一次輪替。

一個容易踩到的交易陷阱

上面那段是「先撤銷，再丟出例外」。Spring 預設遇到例外會把交易整個回滾，連剛撤銷的結果一起退回，偵測就白做了。所以這個方法要寫成 @Transactional(noRollbackFor = InvalidRefreshTokenException.class)，讓撤銷先提交，例外再丟出。

另外「撤銷這顆 token」是一條帶條件的 UPDATE（WHERE revoked_at IS NULL），回傳有沒有真的改到列。兩個請求同時拿同一顆 token 來換，只會有一個成功，另一個得到 false 而被拒絕，不會雙雙成功發出兩組新 token。

登入的小細節

  • 密碼用 BCrypt 雜湊儲存。
  • 帳號不存在和密碼錯誤，回應完全一樣（都是 401 與同一句話），不讓人藉此探測哪些帳號存在。
  • 帳號不存在時，仍然會跟一個假的雜湊比對一次，讓兩種情況花的時間差不多，避免從回應時間猜出帳號是否存在。
  • 兩個角色：ADMIN 與 OPERATOR。沒有自助註冊，開發用的假帳號由設定檔建立。

授權由閘道決定

auth-service 只負責「你是誰」。「你能做什麼」由閘道依 token 裡的 roles 判斷（下一篇），後端各服務信任閘道，自己不再驗證。這是一個刻意記錄下來的限制：後端服務不能直接暴露在外，否則就沒有任何驗證。這個取捨寫在 ADR 0002。

給 .NET 開發者的對照

概念上跟 ASP.NET Core 的 AddJwtBearer 一樣，差別是這裡簽發與驗證分成兩個服務。/.well-known/jwks.json 相當於 OpenID Connect 的 discovery 文件裡的公鑰端點，許多 IdP（Entra ID、Auth0、Keycloak）都用同樣的方式發佈金鑰。

目前已知的限制

  • 沒有「連續登入失敗就鎖帳號」。
  • 過期的 refresh token 還沒有排程清除。
  • 沒有指定私鑰檔時，服務啟動會產生臨時金鑰（只限開發），重啟後舊 token 全部失效。上 Kubernetes 時會把 PKCS#8 格式的私鑰放進 Secret 掛載。

測試

auth-service 共 43 個測試，其中包含一個真的啟動 HTTP 伺服器的端對端測試，從登入、換新到登出走一遍；另外也有針對 refresh token 輪替、BCrypt、RSA 金鑰與 JWT 簽發的單元測試，和用 Testcontainers 的資料庫整合測試。
