失敗處理：業務錯誤不重試，技術錯誤才重試

約 9 分鐘錯誤處理死信佇列

最初的設定很單純：任何例外都重試 3 次（間隔 1 秒、2 秒），仍失敗就進死信佇列。這個做法有兩個問題，看實際的 log 就很明顯。

問題：重試對有些錯誤毫無意義

舉例，機台送來「EQP-ETCH-02 出站 LOT-0004」，但 ETCH-02 手上根本不是這一批。這個錯誤重試十次還是一樣的結果，因為資料不會自己變對。結果是：

  • 白白等了 3 秒（1 秒 + 2 秒）才進死信佇列。
  • 每次失敗印出兩大段 stack trace（一段來自重試用盡，一段來自容器的錯誤處理器），真正的原因淹沒在幾百行裡。

把失敗分成兩種

業務錯誤技術錯誤
例子找不到 lot / 機台、機台不是在處理這批 lot、lot 在 ON_HOLD、欄位缺漏、JSON 壞掉、未知 routing key資料庫暫時連不上、同時更新衝突、網路逾時
重試有用嗎？沒用，輸入就是錯的有用，下一次可能就好了
處理方式立刻進死信佇列重試 3 次（1s、2s），仍失敗才進死信佇列

實作：三個小類別

1. 分類規則 ListenerFailurePolicy：一個純 Java 方法，沿著例外的 cause 鏈檢查（因為框架會把真正的例外包好幾層）。只要鏈上有「業務錯誤」就回傳不可重試：

private static final List<Class<? extends Throwable>> NOT_RETRYABLE = List.of(
        LotNotFoundException.class,
        DuplicateLotNoException.class,
        InvalidLotOperationException.class,
        IllegalArgumentException.class,
        JacksonException.class,              // JSON 解析失敗
        AmqpRejectAndDontRequeueException.class);

2. 一行 log 的收尾者 DeadLetterRecoverer：在「不再重試」時被呼叫，印一行摘要，然後拒收訊息（不放回原佇列），交給死信佇列：

Dead-lettered machine.track-out from equipment-service.machine-events
  (not retryable): InvalidEquipmentOperationException: Equipment EQP-ETCH-02 is not processing lot LOT-0004

3. 接線 ListenerRetryConfig：Spring Boot 本來就會依設定檔建立重試機制，我只用兩個 bean 把「判斷要不要重試」和「最後怎麼收尾」換成自己的：

@Bean
RabbitListenerRetrySettingsCustomizer retryOnlyTechnicalErrors() {
    return settings -> settings.setExceptionPredicate(ListenerFailurePolicy::isRetryable);
}

@Bean
MessageRecoverer deadLetterRecoverer() { return new DeadLetterRecoverer(); }

最後，第二段 stack trace 來自框架的 ConditionalRejectingErrorHandler，我在 application.yaml 把它的 log 等級調到 ERROR，避免同一個失敗被印兩次。

如何確認新版 API

Spring Boot 4 / Spring Framework 7 的重試機制換成了新的 API，網路上多數範例仍是舊版寫法。實作前我直接檢查專案打包出來的 jar，確認 RetryPolicySettings 提供 setExceptionPredicate 才動手。面對版本很新的函式庫，以實際依賴為準最可靠。

給 .NET 開發者的對照

這就是 Polly 的概念：Handle<TransientException>() 只重試暫時性錯誤，其他直接放棄。死信佇列則相當於 Azure Service Bus 的 dead-letter sub-queue。

測試

兩個服務各加了 6 個單元測試，涵蓋：被包起來的業務例外仍判定為不重試、缺欄位、真實的 JSON 解析錯誤、技術錯誤會重試、log 取最內層原因、收尾者丟出的例外沒有 cause 且不含換行。重試判斷是純函式，所以完全不需要開 RabbitMQ 就能測。

如何手動驗證

  1. 啟動 RabbitMQ 與兩個服務。
  2. 在管理介面對 fab.events 發一則 machine.track-out，lotNo 填不存在的值、eventId 用新的 UUID。
  3. 預期：立刻進 .dlq（沒有 1 秒、2 秒的等待），終端機只有一行 Dead-lettered ...。

這一次學到的

  • 重試是為了「暫時性」問題；對「確定性」錯誤重試只是拖延。
  • log 是給人讀的：一行摘要加原因，比一百行 stack trace 有用。詳細資訊仍可在死信佇列裡看到原始訊息。
  • 分類規則放在一個地方、寫成純函式，就能被完整測試。
