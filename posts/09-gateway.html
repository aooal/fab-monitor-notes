第 3 週（三）：api-gateway 與操作台

約 12 分鐘API GatewayVueCORS

服務越來越多，瀏覽器不該知道四個不同的埠號，每個服務也不該各自重寫一遍登入檢查。這篇講 api-gateway（唯一的對外入口）與我做的小型操作台（ops-console）。

閘道做兩件事

  1. 轉發：所有請求打 localhost:8080，閘道依路徑轉給對的服務。
  2. 把關：驗證 access token，並依角色決定能不能呼叫。
路徑轉發到
/api/auth/**auth-service(8084)
/api/lots/**lot-service(8081)
/api/equipment/**equipment-service(8082)
/api/alarms/**alarm-service(8083)

我用的是 Spring Cloud Gateway 的 MVC 版（servlet），不是 WebFlux 版。理由很簡單：其他服務都是 servlet，用同一套測試方式與心智模型，不為了一個閘道多學一套反應式程式設計。這個決定記錄在 ADR 0003。

誰能做什麼

所有規則集中在一個類別 SecurityConfig，一眼看得完：

請求需要
登入、換 token、登出、健康檢查不用 token
GET 批次、機台、警報OPERATOR 或 ADMIN
確認警報（POST /api/alarms/*/acknowledge)OPERATOR 或 ADMIN
其他會改變批次或機台的請求ADMIN
沒列出的路徑一律拒絕（連 ADMIN 也不行）

最後一列是「預設拒絕」（deny by default）：新增了路徑卻忘了設規則，結果是打不開，而不是不小心對外全開。

錯誤回應用跟其他服務一致的 RFC 9457 格式：沒帶 token 或 token 無效是 401，有 token 但角色不夠是 403。這兩個要分清楚，401 是「我不知道你是誰」，403 是「我知道你是誰，但你不能做這件事」。

OAuth2TokenValidator<Jwt> validator = new DelegatingOAuth2TokenValidator<>(
        JwtValidators.createDefaultWithIssuer(props.security().issuer()));

驗證時用 auth-service 公開的公鑰檢查 RS256 簽章，同時檢查有沒有過期、發行者（issuer）對不對。token 裡的 roles 會被轉成 Spring Security 的 ROLE_ADMIN 這類權限。

CORS

操作台跑在 localhost:5173，閘道在 localhost:8080，對瀏覽器來說是不同來源，所以閘道要明確允許。我只允許操作台的來源，不開萬用字元。瀏覽器正式請求前會先送一個不帶 token 的 OPTIONS 預檢，閘道要放行它，否則連登入都送不出去。

測試：假的後端 + 真的閘道

閘道的測試會啟動真正的閘道，再用 JDK 內建的小型 HTTP 伺服器假扮「auth-service 的公鑰端點」與四個後端服務。測試自己產生一組 RSA 金鑰來簽 token，於是能涵蓋：沒帶 token、用別把金鑰簽的偽造 token、過期 token、發行者不對、各角色的權限、路徑真的轉到對的服務、登入不需要 token、預檢通過與陌生來源被拒。共 13 個測試，全程不需要資料庫或 Docker。

操作台

終於有一個畫面可以操作整個系統，不用再手打 API 或 Swagger。技術是 Vue 3、Vite、TypeScript，元件用 PrimeVue。功能刻意縮小：

  • 登入，access token 只放記憶體，refresh token 放瀏覽器儲存空間，重新整理頁面不會被登出。
  • 機台清單與狀態；ADMIN 才看得到模擬按鈕（進站、出站、設為 DOWN、恢復）。
  • 警報清單，預設顯示「進行中」（OPEN 與 ACKNOWLEDGED）；OPEN 的警報有「確認」按鈕。
  • 每 5 秒自動更新；錯誤用不會自動消失的彈窗顯示。

自動續期要小心「同時」

因為 refresh token 每次使用就作廢，如果頁面同時有三個請求都收到 401，各自拿同一顆 refresh token 去換，第二個和第三個會被當成「重複使用」，整組 token 被撤銷，使用者被登出。所以續期的函式在進行中時，後來的呼叫都共用同一個進行中的請求：

export function refresh(): Promise<boolean> {
  if (refreshing) return refreshing   // 已經在換了,等同一個結果
  ...
}

這是前端與後端「輪替」設計互相牽動的一個例子。

為什麼機台不能直接 RUN？

我一開始在操作台放了 RUN / IDLE / DOWN 三顆按鈕，按下 RUN 卻回 409：「沒有批次不能 RUN，請用 track-in」。這是領域規則，機台運轉代表上面有一批晶圓，不是一個單純的標籤。所以按鈕改成貼近真實的操作：閒置的機台顯示「進站」（下拉選一個可用的批次），有批次的顯示「出站」，DOWN 的顯示「恢復」。為此我在 equipment-service 補了 track-in 與 track-out 兩個 REST 端點。

「恢復」也依規則決定回到哪裡：還握著批次的回到 RUN，沒有批次的回到 IDLE。

給 .NET 開發者的對照

閘道相當於 YARP（反向代理）加上 JWT Bearer 驗證與授權政策；SecurityConfig 的規則就像 [Authorize(Roles = "...")] 集中寫在一個地方。操作台則對應一個獨立的前端專案（Blazor WASM 或 Angular）呼叫這個 Web API。

已知的限制

  • 後端服務信任閘道，自己不驗證 token，所以不能直接暴露在外（compose 網路或 Kubernetes 內部才安全）。
  • refresh token 放在瀏覽器儲存空間，理論上腳本注入可以讀走；正式環境會改用 HttpOnly cookie。
  • 閘道還沒有限流與請求紀錄。
  • 操作台是每 5 秒輪詢，不是即時推送。
