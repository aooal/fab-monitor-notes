問題與解法：開發中遇到的七個狀況

約 5 分鐘除錯經驗

這篇整理開發過程中遇到的幾個值得記錄的問題，每一項寫「現象 → 原因 → 做法」，方便日後遇到類似狀況時回頭查。

一覽表

#現象原因做法
1機台卡在 DOWN 且仍握著一批 Lot，設回 IDLE 時回 409同時開了兩個模擬器，事件互相干擾全部停掉 → 手動出站 → 設為 IDLE → 清空死信佇列 → 只開一個模擬器
2手動補發的出站訊息沒有效果重複使用舊的 eventId，被冪等機制當成重複而略過手動送訊息時每次換新的 UUID
3lot.created 發出了，批次卻沒有建立發布當下沒有任何 queue 綁定該 routing key，訊息被丟棄且不報錯固定啟動順序：RabbitMQ → 各服務 → 模擬器
4track-in 找不到 lot 時，是否該自動建立？建立 Lot 需要產品代號與數量，track-in 事件沒有這些資料新增 lot.created 事件，由資料來源負責宣告批次誕生
5模擬器每次重啟都要手動重設機台模擬器自己記一份狀態，與 equipment-service 的真實狀態不一致啟動時先向 equipment-service 讀取真實狀態再開始
6CI 為整合測試設定了不必要的資料庫服務整合測試已改用 Testcontainers，自己啟動容器移除 workflow 中的資料庫服務並加上說明
7失敗訊息白等 3 秒，且印出兩大段 stack trace所有例外一律重試，兩個框架元件各印一次區分業務錯誤與技術錯誤、單行 log（見上一篇）

三個最重要的觀察

1. 同一份狀態存兩處，就需要同步機制（#1、#5）

模擬器存一份機台狀態，equipment-service 也存一份。兩者一旦不同步，系統就進入矛盾狀態，只能手動修復。原則是：狀態要嘛只有一份真相，要嘛有明確的同步方式。這個問題最後促成了「啟動時對齊」。

2. 靜默失敗最難排查（#3）

訊息因為沒有 queue 綁定而消失，系統完全不報錯。RabbitMQ 提供 mandatory 旗標與 publisher return 機制，可以偵測無法路由的訊息。目前先以固定啟動順序規避並寫入文件，之後可以讓發布端在無法路由時記錄警告。

3. 錯誤要能被重現、被看見（#7）

模擬器刻意送出的壞訊息，提供穩定的素材來觀察失敗路徑；而 log 太長就等於沒有 log，一行摘要加原因才算可觀測。

排查順序

遇到「系統狀態不對勁」時，先確認有沒有多個副本同時在跑（#1），再確認服務是不是用新版本重新啟動了，最後才往更深處查。多數問題在前兩步就能釐清。
