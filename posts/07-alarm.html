第 3 週（一）：alarm-service，用規則把事件變成告警

約 10 分鐘告警策略模式PostgreSQL

第 3 週的第一塊是 alarm-service：訂閱機台狀態的變化，依「規則」決定要不要開告警，機台恢復時自動關閉，操作員可以確認（acknowledge）。這篇講規則怎麼設計、告警的狀態與資料庫怎麼把關，以及一個我自己漏掉、靠實際操作才發現的 bug。

需求

  • 機台變成 DOWN 時，產生一筆 OPEN 告警。
  • 操作員看到後按「確認」，告警變成 ACKNOWLEDGED（代表有人接手，不代表機台已修好）。
  • 機台離開 DOWN（恢復）時，告警自動變成 CLOSED，不論有沒有人確認過。
  • 同一台機台同時只能有一筆「進行中」的同類告警，重複送來的 DOWN 不能產生第二筆。

告警的三個狀態

狀態意思誰讓它變成這樣
OPEN已發生，還沒有人看過規則被觸發
ACKNOWLEDGED有人看過並接手，原因可能還在操作員按確認（只能從 OPEN 確認）
CLOSED原因消失機台恢復，系統自動關閉

把「有人看過」和「問題解決」分成兩個狀態很重要：值班的人要知道哪些告警已經有人處理，但也不能因為按了確認，就以為機台好了。

規則：一個介面，一個實作一種告警

「什麼情況要開告警」會一直增加（機台當機、溫度過高、連續失敗……），所以我不把判斷寫死在服務裡，而是做成一個介面，每種告警一個實作，這就是策略模式（Strategy）：

public interface AlarmRule {
    String code();                                        // 例如 EQUIPMENT_DOWN
    boolean raisedBy(EquipmentStatusChange change);       // 這次變化要開告警嗎?
    boolean resolvedBy(EquipmentStatusChange change);     // 這次變化代表原因消失了嗎?
    String describe(EquipmentStatusChange change);        // 給操作員看的訊息
}

目前只有一條規則 EquipmentDownRule：

public boolean raisedBy(EquipmentStatusChange change) {
    return change.to() == EquipmentStatus.DOWN && change.from() != EquipmentStatus.DOWN;
}

public boolean resolvedBy(EquipmentStatusChange change) {
    return change.from() == EquipmentStatus.DOWN && change.to() != EquipmentStatus.DOWN;
}

應用層只認識介面。Spring 會把所有 AlarmRule 的實作收集成一個 List<AlarmRule> 注入，事件進來時逐條詢問。想新增一種告警，只要新增一個類別並註冊成 bean，服務本身一行都不用改。

給 .NET 開發者的對照

這等於把同一個介面 IAlarmRule 在 DI 容器註冊多次，再用 IEnumerable<IAlarmRule> 注入。Spring 的 List<AlarmRule> 就是它的對應。

處理一個事件：同一個交易裡做完

@Transactional
public void onStatusChanged(UUID eventId, EquipmentStatusChange change) {
    if (!processedEvents.markProcessed(eventId, now)) {   // 重複的訊息直接略過
        return;
    }
    for (AlarmRule rule : rules) {
        if (rule.resolvedBy(change)) close(change.equipmentId(), rule, now);
        if (rule.raisedBy(change))   raise(change, rule, now);
    }
}

「記錄這個事件已處理」和「開、關告警」放在同一個交易，要嘛全成功，要嘛全部退回。這跟第 4 篇的冪等消費是同一個做法，訊息重送時不會多開告警。

資料庫是最後一道防線

程式裡已經檢查「這台機台有沒有進行中的告警」，但兩個事件如果幾乎同時進來，兩邊都可能看到「沒有」。所以我另外用資料庫的部分唯一索引（partial unique index）把關：

CREATE UNIQUE INDEX uq_alarm_active_per_equipment_rule
    ON alarm (equipment_id, rule_code)
    WHERE status <> 'CLOSED';

意思是：只對「還沒關閉」的列要求 （機台， 規則） 不重複。已關閉的歷史告警可以有很多筆，進行中的永遠只有一筆。程式邏輯寫給人看，資料庫約束寫給「萬一」。

REST 與事件

方法與路徑用途
GET /api/alarms?status=&equipmentId=查詢，兩個條件都可省略
GET /api/alarms/{id}單筆
POST /api/alarms/{id}/acknowledge確認，body 是 {"acknowledgedBy": "..."}；非 OPEN 的告警回 409

事件這邊，alarm-service 自己宣告 queue alarm-service.equipment-events，綁定 equipment.status-changed，失敗處理與前兩個服務一致（業務錯誤直接進死信佇列，技術錯誤重試三次）。

一個靠實際操作才發現的 bug

單元測試和整合測試全過了，我手動呼叫機台的 REST API 把 EQP-ETCH-01 改成 DOWN，結果 alarm-service 的告警列表是空的。

查下去，原因是 equipment-service 裡有兩條路可以改變機台狀態：一條是處理 RabbitMQ 事件（會發布 equipment.status-changed），另一條是 REST API。我只在第一條加了發布事件，REST 這條漏了。所以從 REST 改狀態，資料庫變了，卻沒人通知 alarm-service。

修法是把「狀態改變就發布事件」放進兩條路共用的那段程式，並補了單元測試（用一個只會記錄的假發布者，驗證各種操作發出了什麼事件）。

這次學到的

如果同一個結果可以從好幾個入口觸發，它的「副作用」（發事件、寫稽核紀錄）就要放在共用的地方，不要放在其中一個入口。另外，各服務的測試各自通過，不代表串起來是對的，所以才需要像操作台這樣能從頭操作一次的畫面。

順帶一提，這也順便碰到了第 7 篇提過的「啟動順序」限制：如果 alarm-service 還沒啟動過，它的 queue 還不存在，先發出去的事件就會消失。解法一樣是先啟動所有消費者，之後會用 Outbox 模式根本解決。

測試

alarm-service 共 45 個測試：規則本身的單元測試、告警狀態轉換、應用層用假的 repository 測流程、ArchUnit 守分層、監聽器的失敗分類，以及用 Testcontainers 啟動真的 PostgreSQL 做的資料庫整合測試。

如何手動驗證

  1. 啟動 RabbitMQ、各資料庫，再依序啟動 alarm-service、equipment-service。
  2. 把機台設為 DOWN（之後有操作台，不必再手打 API）。
  3. 查 GET /api/alarms，應該看到一筆 OPEN 的 EQUIPMENT_DOWN。
  4. 再把機台恢復，同一筆告警會變成 CLOSED。
