業界怎麼做?SECS/GEM、MQTT、Kafka 與雲端服務對照

約 8 分鐘業界對照KafkaMQTT

做模擬專案的人最常被問(也最常問自己)的就是:「真實的系統是這樣嗎?」這篇是我整理的一些概念對照。這些是一般性的公開技術知識,不是任何特定公司內部做法的描述。

SECS/GEM 與我們的事件匯流排,不在同一層

半導體設備與工廠系統之間的標準通訊協定是 SECS/GEM(SEMI 組織制定的 SECS-II 訊息格式與 GEM 行為規範,常透過 HSMS 在 TCP/IP 上傳輸)。它處理的是機台 ↔ 主機(Host)這一段:機台回報事件、狀態、警報,主機下達命令與配方。

我的 Fab Monitor 在更上面一層:假設事件已經從機台出來了,這些事件如何在企業內部的服務之間流動與被處理。所以:

層次常見技術在我的專案
機台 ↔ 主機SECS/GEM(HSMS)由模擬器取代(它直接發事件)
主機 / 閘道 → 服務之間訊息佇列、事件串流(RabbitMQ、Kafka、雲端服務)RabbitMQ
服務對外REST / gRPCREST + Swagger

如果要讓模擬更貼近現實,可以在模擬器前再加一層「把 SECS/GEM 風格的事件轉成內部事件」的轉接器,這會是不錯的擴充方向。

AMQP 還是 MQTT?

我用的是 AMQP 0-9-1(RabbitMQ 的原生協定),不是 MQTT。兩者定位不同:

  • AMQP:功能完整的企業訊息協定,有 exchange、routing、佇列、確認、死信。適合服務之間可靠的工作流。
  • MQTT:極輕量的發布/訂閱協定,為弱網路、小裝置設計。適合大量感測器上報高頻遙測資料。

兩者並不衝突:RabbitMQ 也有 MQTT 外掛。若之後想模擬感測器遙測(溫度、壓力等高頻資料),MQTT 會是自然的選擇,可以在新增「telemetry」功能時再引入。

如果不用 RabbitMQ,exchange 和 queue 會變成什麼?

概念可以對應,但名稱與模型不同。以下是大致的對照(各產品細節仍有差異,選用前請查官方文件):

我學到的概念Apache KafkaAzure Service BusAWS
發布者送訊息的目的地(exchange)TopicTopicSNS Topic / EventBridge 事件匯流排
消費者各自的信箱(queue)Consumer Group(各自維護讀取位置)SubscriptionSQS Queue(訂閱在 SNS 上)
依標籤分送(routing key / binding)通常用不同 Topic 或 partition keySubscription 的過濾規則EventBridge Rule / SNS 過濾政策
死信佇列需自行設計 dead-letter topic內建 dead-letter sub-queueSQS Dead-letter Queue

最大的差別在於模型:RabbitMQ 是「訊息被消費就從佇列消失」;Kafka 是「事件寫進日誌,消費者各自記錄讀到哪」,資料可以保留並重播。這也是為什麼需要「事件回放」或超高吞吐量時常選 Kafka,而需要靈活路由與逐則確認的工作流則常用 RabbitMQ 或雲端佇列服務。

給 .NET 開發者的對照

在 Azure 上,你最常碰到的是 Service Bus(對應 RabbitMQ 的工作流)與 Event Hubs(對應 Kafka 的串流)。學會 RabbitMQ 的概念,換到 Service Bus 時其實只是換名詞。

怎麼「看見」佇列?

RabbitMQ 有內建管理介面。換成其他系統,通常有對應工具:

  • Kafka:Kafka UI、Redpanda Console、AKHQ 等,可以看 topic、partition 與 consumer lag。
  • Azure Service Bus:Azure Portal 與 Service Bus Explorer 可以看佇列長度、死信內容。
  • AWS SQS:Console 可以看可見/不可見訊息數,並可以 poll 看內容。
  • 共通的監控:Prometheus + Grafana 把「佇列長度、消費延遲、死信數量」做成看板。這也是這個專案第 6 週要做的事(RabbitMQ 有 Prometheus 外掛可以直接輸出指標)。
