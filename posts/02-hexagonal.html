第 1 週：用六角架構寫出第一個服務 lot-service

約 12 分鐘Spring Boot六角架構C# 對照

第一週的目標是完成 lot-service：管理 Lot 的生命週期，對外提供 REST API，資料存在 PostgreSQL。重點不在功能多寡，而在把分層做對，讓後續的服務都能沿用同一套結構。

Lot 的狀態機

一批 Lot 有四種狀態，轉換有規則，不是想改就改：

狀態意義可以去哪
CREATED剛建立，尚未進站進站 → IN_PROCESS
IN_PROCESS加工中換站、暫停（ON_HOLD，必須填原因）、完成（COMPLETED）
ON_HOLD被擋住，不可加工釋放後回到加工中
COMPLETED已完成終點

這些規則寫在領域物件 Lot 裡面。非法的轉換（例如已完成的批次又進站）會丟出 InvalidLotOperationException。規則放在物件自己身上，而不是散在 Controller 或 Service 的 if/else 裡。

四層結構

我用「套件」來分層（同一個 Maven 模組，靠規則守住邊界）：

com.shawn.fabmonitor.lotservice
├── domain          Lot、LotNo、狀態機、Repository 介面(port)
├── application     LotService:組合領域物件完成一個用例、管交易
├── web             LotController、DTO、例外轉 HTTP 狀態碼
├── messaging       RabbitMQ 監聽(第 2 週加入)
└── infrastructure
    └── persistence JPA Entity、Repository 實作(adapter)

依賴方向只有一個：外層認識內層，內層不認識外層。domain 最乾淨，甚至不知道 Spring 與資料庫存在。

給 .NET 開發者的對照

把它想成 Clean Architecture / Onion Architecture：

  • domain ≈ 純 C# 的 Domain 專案（實體、值物件、ILotRepository 介面）
  • application ≈ Application 專案（service / use case，@Transactional 像 TransactionScope）
  • web ≈ Controller 與 DTO（@RestController ≈ [ApiController])
  • infrastructure.persistence ≈ EF Core 的 DbContext 與 Repository 實作

差別只在於：Java 這邊我把四層放在同一個專案、用套件分，靠測試守界線；在 .NET 通常拆成多個 csproj，由專案參照在編譯期擋住。

Repository：介面在 domain，實作在 infrastructure

這是六角架構（Ports and Adapters）的核心。領域層只定義「我需要什麼」（port），基礎設施層負責「怎麼做」（adapter）：

// domain:只說需要什麼
public interface LotRepository {
    Optional<Lot> findByLotNo(LotNo lotNo);
    Lot save(Lot lot);
    List<Lot> findRecent(LotStatus status, int limit);
}

實作 LotRepositoryAdapter 在 infrastructure，內部用 Spring Data JPA。好處是：測試時我可以用一個記憶體版的假實作，完全不需要資料庫，就能測領域與應用邏輯。

用 ArchUnit 把規則寫成測試

「領域層不能依賴 Spring」這種規則，靠口頭約定很快會被破壞。ArchUnit 可以把它寫成單元測試，違反就紅燈：

noClasses().that().resideInAPackage("..domain..")
    .should().dependOnClassesThat().resideInAnyPackage("org.springframework..", "jakarta.persistence..")

目前有六條規則：domain 不依賴框架與外層；application 不依賴 web、infrastructure、messaging，也不依賴 AMQP 與 JSON 函式庫；messaging 不依賴 web 與 infrastructure；web 不可以直接使用 persistence 或 Repository 介面。

給 .NET 開發者的對照

ArchUnit 就是 Java 版的 NetArchTest。如果你習慣用專案參照擋分層，ArchUnit 是在「同一個專案裡」做到一樣的事。

資料庫：Flyway 與 optimistic locking

  • 表結構交給 Flyway。SQL 放在 db/migration/V1__...sql，啟動時自動套用；Hibernate 設成 ddl-auto: validate，只負責檢查而不改表。對應 EF Core 的 Migrations，但寫的是原生 SQL。
  • 樂觀鎖。Lot 有 version 欄位，兩個請求同時改同一批，後到的會失敗（LotConcurrentModificationException），而不是默默覆蓋。對應 EF Core 的 concurrency token / rowversion。

測試：不用 mock 資料庫

整合測試用 Testcontainers：測試啟動時自己拉起一個真的 PostgreSQL 容器，跑完就丟掉。這樣測到的是真實的 SQL 與 Flyway，而不是假的。

API 與文件

Controller 提供建立、查詢、進站（track-in）、換站（move）、暫停（hold）、釋放（release）、完成（complete）等端點，並用 SpringDoc 自動產生 Swagger 頁面，不用另外維護文件。錯誤由 ApiExceptionHandler 統一轉成適當的 HTTP 狀態碼（找不到 → 404、非法狀態轉換 → 409、參數錯誤 → 400）。

這一週學到的

  • 分層的目的，是把「可以替換的東西」（資料庫、框架）和「必須穩定的東西」（業務規則）分開。
  • 分層規則要有測試守著，否則隨著功能增加，跨層呼叫很容易悄悄出現。
  • Spring Boot 的「慣例優於設定」跟 ASP.NET Core 很像，多數事情加個 starter 依賴就好了。
