第 2 週：用 RabbitMQ 把服務串起來

約 12 分鐘RabbitMQ事件驅動

第二週的主題是讓服務之間能傳遞事件：機台狀態改變，lot-service 要知道；機台進站，批次要跟著更新。我選擇用 RabbitMQ 傳事件，而不是讓服務互相呼叫對方的 REST API。

為什麼用訊息，而不是直接呼叫 REST？

  • 解耦。發送者不需要知道有誰在聽。之後加 alarm-service，只要多訂閱，不用改 equipment-service。
  • 容錯。lot-service 暫時關掉時，訊息會留在佇列裡，等它回來再處理。如果是 REST，呼叫當下對方沒開就失敗了。
  • 削峰。機台事件一次湧進來，佇列先接住，消費者按自己的速度處理。

代價是流程變成非同步，除錯與一致性都比較複雜，這也是這個專案想練習的重點。選用 RabbitMQ 的完整理由記錄在 ADR 0001。

四個名詞一次搞懂

名詞角色郵局比喻
Exchange收訊息、依規則分送，自己不存訊息郵局分信櫃檯
Queue真正存放訊息的地方，消費者從這裡取收件人的信箱
Bindingexchange 與 queue 之間的規則「這種信放這個信箱」
Routing key訊息上的標籤，配合 binding 決定去向信封上的類別

發布者只對 exchange 說話（fab.events，topic 型），帶上 routing key（例如 machine.track-in）。每個服務自己準備一個 queue，並綁上它關心的 routing key，就只會收到想要的事件。

給 .NET 開發者的對照

如果你用過 MassTransit 或 Azure Service Bus：exchange + routing key 接近 Service Bus 的 topic，每個服務自己的 queue 接近 subscription。@RabbitListener 大致就是一個 consumer / message handler。

事件契約：先寫文件，再寫程式

多個服務共用的事件格式，我寫在 docs/event-contract.md，雙方都以它為準。每則事件都有相同的外層信封：

{
  "eventId": "8f1c...-uuid",
  "type": "machine.track-in",
  "schemaVersion": 1,
  "occurredAt": "2026-10-08T15:31:09Z",
  "equipmentId": "EQP-ETCH-01",
  "lotNo": "LOT-10081531-0001",
  "step": "ETCH"
}

eventId 讓消費者能辨識「這則我處理過了」（下一篇的重點）；schemaVersion 讓格式日後可以演進。

事件內容誰發 → 誰收
lot.createdlotNo、productCode、quantity模擬器 → lot-service
machine.track-inequipmentId、lotNo、step模擬器 → equipment-service、lot-service
machine.track-outequipmentId、lotNo、nextStep（沒有下一站則為 null）模擬器 → equipment-service、lot-service
machine.statusequipmentId、status、reason模擬器 → equipment-service
equipment.status-changedequipmentId、from、to、reasonequipment-service → alarm-service（第 3 週）

Queue 由「消費者」宣告

每個服務啟動時，自己宣告它需要的 queue 與 binding（Spring AMQP 的 Declarables bean）。好處是服務自給自足，不依賴手動設定。

這帶來一個陷阱

如果訊息發出的當下，沒有任何 queue 綁定這個 routing key，訊息會直接消失，不報錯。所以啟動順序必須是：RabbitMQ → lot-service → 模擬器。實測時就遇過模擬器先啟動，lot.created 全部消失，後面的 track-in 因為找不到批次而失敗。細節見「問題與解法」。

死信佇列（DLQ）

處理不了的訊息不能無限重試，也不能默默丟掉。做法是：拒收時不放回原佇列，改由 RabbitMQ 轉送到死信交換器 fab.events.dlx，再以 <queue>.dlq 為 routing key 落進對應的死信佇列。人可以進 RabbitMQ 管理介面查看、分析、必要時重送。

// 宣告 queue 時指定死信去向
QueueBuilder.durable(MACHINE_EVENTS_QUEUE)
    .deadLetterExchange(DEAD_LETTER_EXCHANGE)
    .deadLetterRoutingKey(MACHINE_EVENTS_DLQ)
    .build();

順序保證有限

同一個 queue、單一消費者時，訊息按發布順序處理。但只要把消費者擴成多個，或失敗的訊息被重試而後面的先過，順序就會亂。所以處理程式必須能承受「晚到」或「重複」的事件：遇到不合理的狀態，就丟進死信佇列，而不是硬改資料。契約文件有一節專門寫這個限制。

這一週學到的

  • 訊息系統的難點不在「怎麼送」，而在「送壞了、送兩次、順序亂了怎麼辦」。
  • 事件格式是服務之間的合約，應該像 API 一樣被文件化與版本化。
  • RabbitMQ 內建的管理介面很適合用來學習，可以直接看到 exchange、queue 與訊息的流動。
