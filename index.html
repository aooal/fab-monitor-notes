讓機台資料在
微服務之間流動

Fab Monitor 用假資料模擬工廠機台與批次（Lot）之間的事件交換，情境取材自晶圓廠：機台進站、出站、故障，服務之間用訊息佇列溝通。這裡記錄我怎麼設計、為什麼這樣做、遇到哪些問題，也寫給之後回頭複習的自己。

事件怎麼流動

模擬器假裝是機台，把事件丟到同一個 exchange。各個服務分別訂閱自己需要的事件，處理不了的訊息進死信佇列，等人處理。

第 1 週：用六角架構寫出第一個服務 lot-service

從 C#/.NET 的視角看 Spring Boot：領域、應用、Web、基礎設施四層，以及用 ArchUnit 把分層規則寫成會失敗的測試。

exchange、queue、binding、routing key、死信佇列各是什麼？事件契約怎麼訂？為什麼 queue 要由消費者宣告？

約 12 分鐘 · RabbitMQ / 事件驅動 NOTE 04

訊息會重複送達：冪等消費與交易

at-least-once 意味著同一則訊息可能來兩次。processed_event 表、ON CONFLICT DO NOTHING 與「同一個交易」的設計。

約 9 分鐘 · 冪等 / 交易 / PostgreSQL NOTE 05

機台模擬器：沒有真機台，就自己造事件

可重現的隨機、故意送壞訊息、啟動時對齊真實狀態；以及「找不到 lot 要不要自動建立」的設計取捨。

約 10 分鐘 · 模擬器 / 設計取捨 NOTE 06

失敗處理：業務錯誤不重試，技術錯誤才重試

把失敗分成兩種，各走各的路；再把兩大段 stack trace 縮成一行 log。

約 9 分鐘 · 錯誤處理 / 死信佇列 NOTE 07

第 3 週（一）：alarm-service，用規則把事件變成告警

策略模式的告警規則、OPEN / ACKNOWLEDGED / CLOSED 三種狀態、資料庫的部分唯一索引，以及一個靠實際操作才發現的事件漏發 bug。

約 10 分鐘 · 告警 / 策略模式 / PostgreSQL NOTE 08

第 3 週（二）：auth-service，RS256 JWT 與會輪替的 refresh token

為什麼用非對稱簽章、access token 為什麼只有 15 分鐘、refresh token 怎麼偵測被偷走，以及一個容易踩到的交易回滾陷阱。

約 11 分鐘 · JWT / 安全 / Spring Security NOTE 09

第 3 週（三）：api-gateway 與操作台

唯一的對外入口、集中的角色規則、401 與 403 的差別，以及用 Vue 3 做的小型操作台：為什麼機台不能直接 RUN。

約 12 分鐘 · API Gateway / Vue / CORS NOTE 10

第 4 週：Docker、compose 與 CI，一行指令跑起整個系統

兩階段 Dockerfile、只開三個對外的門、用健康檢查決定啟動順序、一個看起來像錯誤的資料庫 log，以及把映像檔推到 GHCR。

約 10 分鐘 · Docker / docker compose / CI NOTE 11

第 5 週：Kubernetes 與 Helm，讓系統自己修復、滾動更新與擴縮

kind 本機叢集、探針與 init container、滾動更新擋下壞版本、HPA 自動擴縮、把 JWT 金鑰放進 Secret，以及用 Helm 打包與回滾。

約 13 分鐘 · Kubernetes / Helm / kind NOTE 12

第 6 週（一）：CI 部署冒煙測試，每次都在新叢集上把系統裝起來

為什麼單元測試抓不到部署問題、冒煙測試的八個步驟、用 values-ci.yaml 配合小機器、把「換掉 auth-service 後 token 仍有效」變成自動檢查。

約 9 分鐘 · GitHub Actions / kind / Helm / CI NOTE 13

第 6 週（二）：Prometheus 與 Grafana，看見有沒有人漏掉警報

指標怎麼從 Spring Boot 流到儀表板、從資料庫算出的警報業務指標、Kubernetes 上的服務探索、同一組檔案給 compose 與 Helm，以及跑起來後死信佇列被看見的那一刻。

互動實驗室

不用安裝任何東西，直接在瀏覽器裡操作。這裡是用前端程式碼模擬的小版本，規則照專案的設計寫，不是連到真正的 RabbitMQ。

事件流沙盒

依序按「建立批次 → 進站 → 出站」看事件怎麼流動；再試試「重送上一則」（冪等）、「送壞訊息」（直接進死信佇列）與「資料庫閃斷」（技術錯誤才會重試）。

Lot 狀態機

點按鈕改變批次的狀態。不合法的操作會被拒絕，對應 REST API 回傳的 409。

六週進度

計畫分六週，每週一個可展示的成果。

第 1 週 · lot-service 完成

批次的狀態機、REST API、PostgreSQL、Flyway、六角架構與 ArchUnit、GitHub Actions CI。

第 2 週 · equipment-service、模擬器、RabbitMQ 完成

機台服務、事件契約、冪等消費、死信佇列、機台模擬器、lot-service 訂閱事件、業務錯誤直接進死信佇列。

第 3 週 · alarm-service、auth-service、api-gateway、操作台 完成

機台 DOWN 時產生告警、恢復時關閉、可確認；RS256 JWT 與輪替的 refresh token；唯一的對外閘道與角色規則；Vue 3 操作台。

第 4 週 · Docker 與 CI 完成

每個服務的 Dockerfile、一行指令啟動整個系統、CI 推映像檔到 GHCR；警報記錄「誰關的」並標出沒人處理的警報，模擬器改成更貼近真實的故障。

第 5 週 · Kubernetes 與 Helm 完成

kind 本機叢集、探針與啟動順序、滾動更新與回滾、HPA 自動擴縮、JWT 簽章金鑰放進 Secret、Helm chart（install / upgrade / rollback）。

第 6 週 · CD、監控、文件 進行中

已完成：CI 部署冒煙測試（拋棄式 kind 叢集 + Helm 安裝 + 登入與機台清單檢查）、Prometheus + Grafana 看板與告警規則（含「沒人確認的警報」指標）。接下來：README 架構圖與示範影片、警報升級規則、ADR 收尾。
